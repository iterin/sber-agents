## Отчёт по MCP серверу и новому инструменту

### Какой новый инструмент вы реализовали?

Я реализовал новый MCP‑инструмент `calculate_deposit_profit` в сервере `mcp-bank-agent`.  
Он добавлен в файл `mcp/mcp-bank-agent/server.py` и экспортируется как обычный MCP tool через `@mcp.tool`.

### Как работает ваш инструмент? Примеры использования

Инструмент рассчитывает доходность банковского вклада по заданным параметрам:
- **initial_amount** — начальная сумма вклада в рублях (от 1 000);
- **annual_rate** — годовая процентная ставка в процентах (0–100);
- **term_months** — срок вклада в месяцах (1–60);
- **capitalization** — флаг капитализации процентов (ежемесячное начисление процентов на проценты).

Логика работы:
- если **capitalization = true**, используется формула сложных процентов с ежемесячной капитализацией:
  \[
  S = P \cdot (1 + r_{m})^{n}, \quad r_{m} = \frac{r_{\text{год}}}{12}
  \]
- если **capitalization = false**, используется простая схема без капитализации:
  \[
  S = P \cdot \left(1 + r_{\text{год}} \cdot \frac{n}{12}\right)
  \]
- дополнительно вычисляется эффективная годовая ставка (APY) на основе фактического срока:
  \[
  r_{\text{эфф}} = \left(\frac{S}{P}\right)^{12/n} - 1
  \]

На выходе инструмент возвращает человекочитаемую строку с:
- исходными параметрами;
- итоговой суммой на конец срока;
- размером дохода;
- эффективной годовой ставкой в годовых процентах.

**Примеры использования:**

1. Вклад 100 000 ₽ на 12 месяцев под 10% без капитализации:

```python
calculate_deposit_profit(
    initial_amount=100_000,
    annual_rate=10.0,
    term_months=12,
    capitalization=False,
)
```

2. Вклад 500 000 ₽ на 24 месяца под 15% с ежемесячной капитализацией:

```python
calculate_deposit_profit(
    initial_amount=500_000,
    annual_rate=15.0,
    term_months=24,
    capitalization=True,
)
```

3. Короткий вклад 200 000 ₽ на 3 месяца под 8% с капитализацией:

```python
calculate_deposit_profit(
    initial_amount=200_000,
    annual_rate=8.0,
    term_months=3,
    capitalization=True,
)
```

### Подключали ли MCP сервер к другим клиентам? Как это работало?

MCP‑сервер `mcp-bank-agent` подключён к Telegram‑боту через LangChain‑агента:
- в `src/agent.py` используется `MultiServerMCPClient` из `langchain_mcp_adapters.client`;
- клиент подключается к серверу по адресу `http://localhost:8000/mcp` с транспортом `streamable-http`;
- через `mcp_client.get_tools()` автоматически подхватываются все инструменты MCP‑сервера (`search_products`, `currency_converter`, `calculate_deposit_profit`);
- эти MCP‑инструменты добавляются в общий список `tools` ReAct‑агента наряду с локальным инструментом `rag_search`.

Дальше Telegram‑бот передаёт сообщения пользователя в ReAct‑агента (`agent_answer`), а агент сам решает:
- когда вызывать RAG‑поиск по PDF/JSON;
- когда обращаться к MCP‑инструментам, например, к `calculate_deposit_profit` для расчёта доходности вклада.

Фактически MCP‑сервер выступает как внешний источник “живых” банковских данных (продукты, валюты, расчёты), прозрачно интегрированный в одного агента.

### Какие преимущества MCP вы заметили?

- **Ясное разделение ответственности**: основной сервис отвечает за диалог, RAG и бизнес‑логику, а MCP‑сервер — за конкретный домен (банковские продукты, валюты, финансовые расчёты).
- **Лёгкое расширение функционала**: чтобы добавить новый банковский инструмент (как `calculate_deposit_profit`), достаточно дописать одну функцию и задекорировать её `@mcp.tool`, без изменений в коде бота.
- **Унифицированный интерфейс инструментов**: с точки зрения агента MCP‑tools выглядят так же, как локальные LangChain‑инструменты — это упрощает код агента и позволяет легко комбинировать RAG и внешние сервисы.
- **Переиспользуемость**: MCP‑сервер потенциально может быть подключён не только к этому боту, но и к другим клиентам (IDE‑плагины, другие агенты), без дублирования логики расчётов и работы с банковскими продуктами.

### С какими сложностями столкнулись?

- **Редкие глюки LLM при tool‑calling**: в логах были случаи, когда модель возвращала `AIMessage` с пустым `content` и без `tool_calls`, а также ошибки уровня 400 от OpenAI‑совместимого API (`Failed to convert messages to harmony tokens`).  
  Это требовало аккуратного fallback‑поведения в `agent_answer`, чтобы пользователь всё равно получал осмысленный ответ.
- **Диагностика проблем с провайдером LLM**: некоторые ошибки были связаны не с кодом MCP‑сервера, а с внутренней реализацией провайдера (harmony tokens), поэтому приходилось читать стек‑трейсы и понимать, что нужно менять модель/провайдера или параметры, а не логику агента.
- **Согласование форматов**: нужно было следить, чтобы формат текстовых ответов MCP‑инструментов был удобен для конечного пользователя в чате (читаемые числа, пояснения эффективной ставки, чёткие заголовки в ответе).
